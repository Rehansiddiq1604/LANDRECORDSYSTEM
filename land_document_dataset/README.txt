*** IMPORTANT DISCLAIMER ***

Every document image in this dataset is 100% SYNTHETIC and was generated by
a computer program purely for SOFTWARE DEVELOPMENT AND TESTING purposes.

  - NO real person's personal information appears anywhere in this dataset.
    All owner names, previous-owner names, officer names, addresses, survey
    numbers, patta numbers, registration numbers, and dates are fictional
    and were generated/randomized by a script (see generator.py).
  - NO actual government land record, deed, or template has been copied.
    Layout, seals, emblem, and wording were designed from scratch and
    deliberately avoid reproducing any real department's exact format,
    emblem, or seal design.
  - Every document image carries a visible watermark and a footer stripe
    reading "SYNTHETIC TEST DOCUMENT - NOT AN OFFICIAL LAND RECORD" (in
    English and in the document's local language).
  - District names are real Indian geography (public, non-personal
    information) used only for realistic flavour; taluk/tehsil/mandal and
    village names are fictional.
  - This dataset must NEVER be presented as, or mistaken for, real land
    records. It exists solely to test OCR and document-processing
    pipelines during the development of the SIH project referenced above.

================================================================================
 VALIDATION TEST CASES (see metadata/expected_results.json)
================================================================================

Each document was generated against a specific, intentional validation
scenario so the pipeline's cross-validation / anomaly-detection stage has a
known correct answer to check itself against:

  VALID                6 docs  - every key field on the document matches DB
  AREA_MISMATCH         3 docs  - printed area != database area
  OWNER_MISMATCH        3 docs  - printed owner name != database owner name
  SURVEY_MISMATCH        3 docs  - printed survey number != database survey number
  DUPLICATE              4 docs  - 2 pairs; each pair shares identical owner /
                                    survey no / village / area but is filed as
                                    two separate document instances (one pair
                                    is same-language, one pair is cross-language
                                    -- Kannada vs English -- to test multilingual
                                    duplicate/fuzzy-matching)
  MISSING_FIELD          3 docs  - one important field is blank / absent on
                                    the document although present in the DB
  LOW_OCR_QUALITY         3 docs  - heavy combined degradation (noise, blur,
                                    fading, skew, uneven lighting, low JPEG
                                    quality) while field values still match DB
  HISTORICAL_CONFLICT    2 docs  - current document agrees with the current
                                    DB, but conflicts with an older archived
                                    (pre-2005) record -- see the "extra."
                                    "historical_record" block in the JSON
  MULTIPLE_CONFLICT      3 docs  - two or more fields (e.g. owner AND area,
                                    or owner AND survey number) disagree with
                                    the database simultaneously
                                                            -----------------
                                                            TOTAL: 30 docs

For every document, metadata/expected_results.json contains:
  - printed_fields_on_document : what OCR should ideally extract from the
    image (including intentionally wrong / blank values, where applicable)
  - expected_database_record   : the "correct" record your MySQL database
    should hold for that property
  - mismatched_fields / missing_fields : explicit list of which fields differ
  - expected_validation_result : the label your pipeline's final validation
    stage should output
  - notes                      : human-readable explanation

metadata/documents.csv is a flat, spreadsheet-friendly index (doc_id,
filename, language, document_type, validation_case, ocr_challenges, and a
few headline field values) useful for quick filtering/sampling during
development.

================================================================================
 OCR / SCAN CHALLENGES BUILT INTO THE IMAGES
================================================================================

Each document was rendered with a randomized subset (3-6) of the following
realistic degradations/complexities, listed per-document in the
"ocr_challenges" field of both the CSV and the JSON:

  complex_background     faint printed guideline/pattern texture behind text
  stamp_overlap           a circular "office seal" stamp visually overlapping
                          a field row's text
  handwritten_signature   a squiggle/flourish signature drawn in the footer
  handwritten_fields      1-2 field values rendered in a slanted, jittered,
                          "handwritten-ink" style instead of print
  font_size_variation     row label font sizes vary within the same document
  poor_scan               downscale/upscale blur + low-quality JPEG re-encode
  rotation_skew           the whole page is rotated -5.5 deg to +5.5 deg
  noise                   Gaussian sensor noise (+ occasional salt & pepper)
  faded_text               overall contrast is faded toward white (weak ink /
                          old photocopy look)
  uneven_lighting          a radial brightness gradient simulates uneven scan/
                          photograph lighting
  text_near_border        a small reference field is printed right at the
                          inner page margin
  mixed_language          an explicit local-script + English sentence/label
                          is embedded (e.g. Tamil label + English remark),
                          in addition to the baseline mixed-script field
                          values (English/Latin names & numbers are used
                          for several fields even on non-English documents,
                          which is realistic for Indian land records)

LOW_OCR_QUALITY-case documents always force the heaviest combination
(poor_scan + noise + faded_text + uneven_lighting + rotation_skew) so you
have guaranteed "hard" samples to benchmark OCR accuracy against.

================================================================================
 HOW TO USE THIS DATASET TO TEST EACH PIPELINE STAGE
================================================================================

1. OpenCV Preprocessing
   - Use the "rotation_skew", "noise", "poor_scan", and "uneven_lighting"
     tagged documents to test deskewing, denoising, contrast normalization,
     and adaptive thresholding. Compare the corrected image against the
     un-degraded look of a same-language "VALID" document to gauge quality
     of restoration.

2. Multilingual OCR
   - Run your OCR engine (e.g. Tesseract with tam/hin/tel/kan/eng language
     packs, or a multilingual model) against each language folder
     separately and pooled. Use "mixed_language" and "font_size_variation"
     tagged documents to test script-switching within a single page/field.

3. Field Extraction
   - Every document uses the same field-label vocabulary (see
     config.py:TERMS) in the local language, positioned in a left-label /
     right-value table. Use this consistency to test your label->field
     mapper, then validate extracted values against
     "printed_fields_on_document" in expected_results.json.
   - "text_near_border" documents test whether your layout parser correctly
     picks up fields close to the page edge.
   - "MISSING_FIELD" documents test that your extractor correctly reports a
     field as blank/unavailable instead of hallucinating a value.

4. Name Normalization
   - Owner/previous-owner names use varied Indian naming conventions
     (initials before surname, multiple surname styles) -- use these to test
     normalization (case folding, initials expansion/contraction, transliteration
     consistency) before database matching.

5. Fuzzy Matching
   - Use the OWNER_MISMATCH, SURVEY_MISMATCH, and DUPLICATE cases: your fuzzy
     matcher should score the printed value against expected_database_record
     and correctly flag near-duplicates vs. genuine mismatches. The
     cross-language DUPLICATE pair (Kannada <-> English, same property) is
     specifically designed to test transliteration-aware fuzzy matching.

6. Database Validation
   - For every document, compare "printed_fields_on_document" (i.e. whatever
     your OCR + extraction pipeline actually recovers) against
     "expected_database_record". Your validation module's output should
     equal "expected_validation_result".

7. Anomaly Detection
   - HISTORICAL_CONFLICT documents test whether your system checks a
     document not just against the *current* DB row, but against archived/
     historical versions of that property's record (see
     extra.historical_record in the JSON).
   - MULTIPLE_CONFLICT documents test that anomaly detection surfaces *all*
     disagreeing fields, not just the first one found.

8. Risk Scoring
   - Use "ocr_challenges" (image quality signals) together with
     "mismatched_fields"/"missing_fields" (data signals) as combined inputs
     to a risk score. E.g. a VALID document with 5 heavy OCR challenges
     should score "needs manual review" on image-quality grounds alone, while
     a clean-scan OWNER_MISMATCH document should score high risk on data
     grounds. Compare your system's risk tier against validation_case to
     tune thresholds before the final "Explainable Verification Report" and
     "Human Officer Approval" stages.

================================================================================
 SUGGESTED INTEGRATION (Python + FastAPI + MySQL)
================================================================================

  - Load metadata/documents.csv into a `synthetic_documents` staging table
    (doc_id, filename, language, document_type, validation_case,
    ocr_challenges) to drive automated test runs / CI.
  - Load metadata/expected_results.json into a `synthetic_ground_truth`
    table (or keep as JSON fixtures) keyed by doc_id, and use it as the
    "answer key" your FastAPI test suite asserts against after each stage
    (OCR output, field extraction output, validation-engine output).
  - Seed a MySQL `land_records` table with the "expected_database_record"
    values (this is literally the fictional DB your validation stage should
    be checking documents against) -- one row per unique property identity
    (remember the two duplicate pairs intentionally point at the same
    underlying property).
  - Because every filename and JSON key is deterministic and stable, you can
    write straightforward pytest cases like:
      assert pipeline_result[doc_id]["validation"] == ground_truth[doc_id]["expected_validation_result"]

================================================================================
 REGENERATING / EXTENDING THIS DATASET
================================================================================

This dataset was produced by a small Python toolchain (config.py,
doc_specs.py, generator.py, renderer.py, degrade.py, build_dataset.py) using
Pillow + OpenCV + NumPy, with Noto Sans Tamil/Devanagari/Telugu/Kannada
fonts for correctly shaped native-script rendering. The generation is
seeded/deterministic, so re-running build_dataset.py reproduces the same 30
documents; changing the seeds, the LANG_CASES table, or CHALLENGE_POOL in
doc_specs.py lets you scale up the dataset or rebalance the validation-case
distribution for further testing.
